# 剧本 YAML Schema 设计

## 1. 设计目标

本 Schema 用于描述由不少于 3 个小说章节改编得到的结构化剧本。它不只解决“YAML 格式正确”问题，还服务于项目的核心定位：

> 让小说改编结果可控、可追溯、可校验，并能够继续被编辑或交给其他工具处理。

机器可执行的 JSON Schema 位于 [`schema/screenplay.schema.json`](../schema/screenplay.schema.json)，完整有效示例位于 [`examples/screenplay.example.yaml`](../examples/screenplay.example.yaml)。

## 2. 顶层结构

| 字段 | 用途 | 设计原因 |
| --- | --- | --- |
| `schema_version` | 标记结构版本 | 便于未来兼容和迁移 |
| `project` | 剧本基础信息与生成方式 | 明确作品信息，并诚实记录 AI、规则或演示模式 |
| `adaptation_control` | 作者的改编要求 | 让作者在生成前控制忠实度、重点和禁止修改项 |
| `source` | 原小说章节信息 | 满足不少于 3 章的输入要求，并支持章节覆盖计算 |
| `story_bible` | 故事前提、人物与地点 | 为跨章节一致性检查提供稳定实体 |
| `narrative_events` | 从小说提取的关键事件 | 为剧情覆盖计算提供唯一的事件清单 |
| `screenplay` | 场次、动作、对白与旁白 | 表达可编辑的剧本主体 |

## 3. 核心设计原因

### 3.1 作者改编控制

`adaptation_control` 保存作者在生成前做出的选择：

- `fidelity`：忠于原著、平衡改编或自由改编。
- `target_scene_count`：期望生成的场次数。
- `focus`：希望强化冲突、对白、悬念、情感或视觉动作。
- `must_keep_event_ids`：必须保留的小说事件。
- `allow_new_events`：是否允许 AI 新增原著中不存在的事件。
- `forbidden_changes`：明确禁止的改编方向。

普通生成工具常让用户只输入一段提示词，本设计把关键决策结构化，使后端可以检查结果是否遵守作者要求。

人物列表允许为空。系统无法从原文可靠确认人物时，应明确显示“未识别到可靠人物”，不得为了满足结构要求虚构人物。

### 3.2 双向剧情覆盖

每个场次通过 `traceability.source_event_ids` 指向来源事件。系统根据这一项唯一事实动态反向计算每个小说事件被哪些场次采用。

这形成双向覆盖关系：

```text
小说事件 → 剧本场次
剧本场次 → 小说事件
```

系统因此能够识别重要事件遗漏、内容重复改编、章节覆盖不足，以及 AI 自行新增内容。

### 3.3 场次改编证据链

每个场次的 `traceability` 必须包含：

- `origin`：来源改编或 AI 新增。
- `source_chapter_ids`：来源章节。
- `source_event_ids`：来源事件。
- `adaptation_actions`：保留、压缩、合并、重排、改写或新增。

每个来源事件保存原文摘录、字符起止位置和所属章节；每个章节保存原文内容哈希。场次通过事件 ID 连接到这些证据，应用层会根据原文验证摘录位置和内容哈希，避免改编证据被伪造。

本地规则模式会先统一换行符并移除章节正文首尾空白；章节哈希和证据字符位置均基于这一份可展示、可下载的规范化章节正文，而不是原始文件的字节位置。

本地规则模式刻意不猜测人物身份与具体地点，因为仅靠正则无法可靠区分人物、物体、叙事修饰语和抽象地点。它会生成“未指定场景”和人工确认提示；人物、地点与对白分析由作者确认、精品示例或真实 AI 模式完成。

来源改编场次必须提供准确匹配的章节和事件；AI 新增场次不得伪造来源，并由应用层根据 `allow_new_events` 决定是否允许通过质量门禁。

`invent_detail` 表示为了影视化增加雨声、动作等细节，不改变剧情事实；`invent_event` 表示新增剧情事件。作者禁止新增事件时，系统仍可补充可视化细节，但会拦截任何 `invent_event`。

### 3.4 剧本元素显式建模

场次内容没有被保存为一整段文本，而是拆分为 `action`、`dialogue`、`narration` 和 `transition` 四种节拍。

显式建模有三个好处：

1. 用户可以按元素编辑剧本。
2. 系统可以检查无对白场次、角色引用错误等问题。
3. 后续可以扩展导出到 Fountain、分镜或配音工具。

### 3.5 质量门禁

质量报告不写入剧本 YAML，而是由程序根据当前剧本动态计算，避免作者编辑后报告过期。报告包含可复核指标：

- 章节覆盖率。
- 小说事件覆盖率。
- 关键事件覆盖率。
- 必保事件覆盖率。
- 原文溯源率。
- AI 新增场次比例。
- 目标场次数偏差。

每个问题均包含代码、严重程度、消息和关联实体；`passed` 标记当前结果能否通过质量门禁。Schema、引用、证据和作者控制错误都会进入同一份结构化报告。结构非法时系统只返回 Schema 错误，不继续执行依赖完整结构的业务检查，从而保证编辑过程不会崩溃。报告可以单独下载。

首版硬性门禁包括：Schema 合法、引用和证据合法、必保事件全部覆盖、关键事件全部覆盖，以及不违反作者对新增剧情事件的限制。所有来源改编场次还必须在动作文本中逐字保留其来源事件证据，避免作者编辑后通过改写生成模式字段绕过 grounding 约束。

工作台只允许将当前通过质量门禁的版本作为正式剧本 YAML 下载；修改后尚未校验或被门禁阻断的草稿不会被误标为可交付结果。

### 3.6 诚实记录生成方式

`project.generation.mode` 明确区分：

- `qiniu_ai`：七牛 AI 模式。
- `compatible_ai`：其他兼容 AI 服务。
- `local_rules`：本地规则模式。
- `curated_demo`：精品示例模式。

应用层会校验生成元数据的一致性：`qiniu_ai` 必须使用 `qiniu-ai` 提供商并记录非空模型；`compatible_ai` 必须记录非空模型且不能冒用七牛或本地规则提供商；`local_rules` 必须使用 `local-rules` 提供商且模型为空；`curated_demo` 必须使用固定的本地精品示例提供商且模型为空。该设计避免作者编辑 YAML 后把规则结果伪装为 AI 结果，也方便评委复现实验。

## 4. ID 与引用规则

所有可引用实体使用稳定 ID，例如：

```yaml
chapter_1
event_letter_found
character_lin_xia
location_old_station
scene_1
```

ID 必须以小写字母开头，仅包含小写字母、数字和下划线。显示名称可以修改，但 ID 应保持稳定，避免人物改名后破坏场次引用。

## 5. Schema 能力边界

JSON Schema 负责验证字段类型、必填项、枚举值和基础范围，但以下跨对象规则需要由应用层验证器检查：

- `source.chapter_count` 是否等于 `chapters` 的实际数量。
- ID 是否全局唯一。
- 场次引用的人物、地点、章节和事件是否存在。
- 章节原文哈希、事件证据摘录和字符位置是否匹配。
- 场次来源章节是否与来源事件所属章节精确一致。
- 根据场次来源事件动态生成双向剧情覆盖矩阵。
- `must_keep_event_ids` 是否都被剧本覆盖。
- 是否存在作者禁止的新增剧情事件。
- 根据当前剧本动态生成质量报告。

将结构校验和业务一致性校验分开，可以保持 Schema 清晰，并让错误提示更符合用户语言。

## 6. 首版与未来扩展

首版聚焦场次级剧本和可信改编闭环，不包含镜头、拍摄预算、多人协作与视频生成。

未来可在保持兼容的前提下扩展：

- 镜头和分镜结构。
- Fountain、FDX 等剧本格式导出。
- 角色关系和道具追踪。
- 版本差异和作者审核记录。
